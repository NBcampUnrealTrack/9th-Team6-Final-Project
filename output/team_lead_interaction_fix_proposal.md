# 상자·테스트 키·저장/삭제·종료 수정 승인안

상태: 사용자 승인 후 통합 수정 구현 완료(2026-10-03). 신규 2개·수정 16개, Editor/Game 빌드 및 Automation 12개·두 맵 실행 검증 통과. 기존 저장 6개 SHA256 유지 확인. 아래는 승인 당시의 범위이며 결과는 Docs/PrototypeAcceptance.md에 기록했다.

## 1. 사용자가 말한 저장 문제와 확인 결과

증상: 가방의 저장 버튼을 누른 뒤 '수동 슬롯 1~4를 선택하세요' 안내에 따라 키보드 숫자 1~4를 눌렀지만 선택이나 저장이 되지 않는다.

확인한 현재 흐름:

1. 가방의 저장 버튼은 별도 저장 화면을 열지 않고 SavePlayer를 바로 호출한다.
2. 저장/로드에 SelectedSaveSlot 하나를 공유한다. 자동 저장을 선택하거나 불러오면 값이 0으로 남는다.
3. 수동 저장에서 0은 허용하지 않으므로 '수동 슬롯 1~4를 선택하세요'라는 안내가 나온다.
4. 슬롯 버튼은 Pause/Load/Create 화면에만 있고 가방에는 없다.
5. 숫자 1~4는 기존 퀵슬롯 키다. 가방 메뉴에서는 저장 슬롯 선택에 연결되지 않아 반응하지 않는다.

따라서 이번 증상은 **선택할 화면을 열지 않는 저장 버튼 + 안내와 키 동작 불일치 + 저장/로드 슬롯 공유** 문제다. 파일 손상으로 단정하지 않는다.

2026-10-03 읽기 전용 확인: 새 저장 원본 4개(자동, 수동 1·2·4)와 자동 백업 1개의 Version 2 헤더·길이·CRC는 정상이었다. 수동 3은 비어 있고 기존 PlayerPrototype_Auto.sav도 존재한다. 이 검사만으로 게임 상태 의미나 전체 복원이 검증된 것은 아니다.

## 2. 수정 후 저장 화면

가방 또는 메뉴의 '저장', F5는 **전용 저장 화면**을 연다.

- 수동 슬롯 1~4를 항상 표시한다.
- 각 슬롯에 캐릭터 이름, 저장 날짜/시각, 비어 있음/읽기 오류를 표시한다.
- 버튼으로 슬롯을 선택할 수 있다.
- 저장 화면에서는 숫자 1~4로 슬롯 선택, Enter 또는 '선택 슬롯에 저장' 버튼으로 실행한다.
- 선택 즉시 강조 표시하고 버튼에 '수동 2에 저장'처럼 실제 대상을 표시한다.
- 이미 저장이 있으면 대상 이름·슬롯을 표시한 덮어쓰기 확인을 거친다.
- 요청 접수 후 '수동 2 저장 중', 비동기 완료 후 '수동 2 저장 완료'를 표시한다.
- 저장 불가 사유는 전투/대화/이벤트/사망/효과 처리/쓰기 중 등으로 구체적으로 안내한다.
- 저장 중에는 중복 저장·로드·삭제를 막는다.

수동 저장 슬롯과 불러오기 슬롯의 선택값을 분리한다. 자동 저장을 불러와도 수동 저장 선택이 0으로 바뀌지 않는다. F9는 선택한 불러오기 슬롯을 읽는 동작을 유지하며 현재 로드 대상이 보이게 안내한다.

플레이 중 숫자 1~4는 퀵슬롯으로 유지한다. 가방에서는 버튼으로 아이템을 사용하고, 저장 화면에서는 숫자 1~4가 저장 슬롯 선택이다. UI에 포커스가 있어도 해당 화면의 키를 한 번만 처리한다.

새 캐릭터 생성은 기존 설계대로 초기 자동 저장을 만든다. 자동 슬롯에 기존 캐릭터 저장이 있으면 이름과 교체 대상을 알리고 확인한 뒤 생성한다. 이 동작이 선택한 수동 슬롯을 변경하는 것으로 보이지 않도록 명확히 표시한다.

## 3. 저장 삭제

저장/로드 화면에 '선택 슬롯 삭제'를 추가한다. 자동·수동·손상된 파일도 대상 이름/슬롯을 확인한 뒤 삭제할 수 있다.

- 확인창: '수동 2 / 캐릭터 이름의 저장을 삭제할까요?'와 삭제/취소.
- 해당 슬롯의 .sav, .bak, .tmp, .rollback, .bak.tmp만 정확히 처리한다.
- 백업을 남겨 삭제한 슬롯이 목록에 다시 나타나는 문제를 방지한다.
- 삭제 후 파일 존재 여부를 확인하고 슬롯 목록을 갱신한다.
- 일부 파일 삭제 실패 시 성공으로 표시하지 않고 실제 남은 상태와 사유를 안내한다.
- 다른 슬롯과 현재 플레이 상태는 삭제 대상에 포함하지 않는다.
- 자동 저장 삭제 시 보류 요청/타이머를 정리해 바로 다시 생성되지 않게 한다. 이후 플레이 중 자동 저장이 새로 만들어질 수 있다는 점은 확인창에 표시한다.

기존 Version 1 원본은 '기존 저장' 별도 항목으로 표시하고 가져오기/삭제 버튼을 둔다. 원본 삭제와 가져온 수동 슬롯 삭제는 각각 독립된 작업이다. 가져오기 자체는 원본을 보존한다.

이번 수정안 작성 중 실제 사용자 저장 파일은 삭제하지 않았다. 구현·자동 테스트는 IC_Test_ 전용 파일로 수행한다.

## 4. 게임 끝내기

생성 화면과 메뉴에 '게임 끝내기' 버튼을 추가한다.

| 선택 | 동작 |
| --- | --- |
| 저장 후 종료 | 수동 1~4 선택→필요하면 덮어쓰기 확인→비동기 저장 성공 후 종료 |
| 저장 없이 종료 | 진행을 새로 저장하지 않고 종료 |
| 취소 | 이전 화면으로 복귀 |

- 생성 전이나 사망 등 저장 불가 상태에서는 저장 없이 종료/취소를 제공하고 저장 불가 사유를 표시한다.
- 이미 저장 쓰기가 진행 중이면 완료까지 종료를 대기한다.
- 저장 실패 시 게임을 닫지 않고 재시도 또는 저장 없이 종료를 선택할 수 있게 한다.
- 종료 요청 때문에 별도 자동 저장으로 기존 자동 슬롯을 덮어쓰지 않는다.
- 일반 게임 창은 게임 프로세스를 종료한다.
- 에디터 PIE는 현재 플레이 세션만 중지한다. 에디터 전체 종료는 호출하지 않는다.
- PIE 종료를 위해 Editor 빌드에만 UnrealEd 모듈 의존성을 추가하고 WITH_EDITOR 코드로 분리한다. Game/Shipping 빌드에는 해당 의존성을 넣지 않는다.

## 6. 기존 상자 상호작용

현재 F는 카메라 중앙에서 1000cm 단일 선으로 찾는다. 첫 대상이 APlayerPrototypeObject이고 캐릭터와 상자 중심 거리가 250cm 이하일 때만 처리한다. 작은 상자 위를 보거나 다른 물체가 선에 걸리면 가까워도 선택되지 않는다. 카메라는 캐릭터 뒤 420cm, 옆 45cm, 위 65cm에 있다. 실제 시점 재현으로 실패 조건을 확인한다.

수정:

- 캐릭터 기준 상호작용 거리 250cm 유지.
- 중앙 조준의 유효한 상자를 우선 선택.
- 중앙선이 빗나가면 범위 안 전방의 가까운 상자를 시야 방향/거리로 선택.
- 가림 검사로 벽 너머 상자를 열지 않음.
- HUD에 'F : HOME A 창고 열기'처럼 현재 대상 표시.
- F 입력 시 대상을 다시 검증하고 후보 없음·거리·권한·정의되지 않은 행동을 구분해 안내.
- HOME A/B 공유, NPC 창고 권한, 목재·퀘스트 아이템 규칙 유지.

기존 자동 검증은 OpenContainer를 직접 호출해 F 입력 경로를 놓쳤다. 수정 후 실제 상자에 접근해 F 처리→후보 선택→창고 UI/지급까지 검사한다.

앞서 확인한 에디터 로그에는 L_TestMap에서 PlayerPrototypeGameMode로 PIE를 실행한 기록이 있었다. 현재 사용자가 실행한 별도 게임 창은 L_PlayerPrototype으로 확인된다. 두 맵의 기존 프로토 상자를 검증한다. 맵에 놓인 별도 클래스 상자가 발견되면 그 객체와 연결 방법을 구체적으로 기록한다.

## 8. 완료 기준과 구현 순서

1. 저장 UI를 먼저 고친다. 가방 저장 버튼→저장 화면→숫자 1~4 선택→Enter→선택 슬롯 저장 완료 메시지.
2. 자동 슬롯 로드 후 가방 저장도 정상 동작한다. 잘못된 슬롯을 덮어쓰지 않는다.
3. 기존 파일과 다른 슬롯을 유지하며 선택한 테스트 슬롯만 삭제한다. 자동 백업까지 삭제돼 빈 슬롯으로 표시된다.
4. 종료의 세 선택과 저장 완료 대기를 검사한다. 실패한 저장 때문에 창을 바로 닫지 않는다.
5. F6 메뉴·취소와 상자 선택을 수정하고 실제 F 경로를 검증한다.
6. 테스트 파일로 저장→게임 프로세스 정상 종료→새 프로세스에서 로드한다. 캐릭터·아이템·창고·장비·시간 일치를 확인한다.
7. L_PlayerPrototype과 L_TestMap에서 생성·상자·저장 흐름을 검사한다.
8. 컴파일, 기존 공용 테스트, 새 상호작용/삭제 테스트, 프로토 실행 검증을 기록한다.
9. PIE의 실제 F6/종료 동작은 별도로 확인한다. 일반 게임 실행이나 HandleKey 직접 호출만으로 에디터 충돌 해결을 판정하지 않는다.

위 통합 수정안 전체의 승인을 받아 구현·검증을 완료했다. 실제 사용자 저장 삭제는 수행하지 않았다.
